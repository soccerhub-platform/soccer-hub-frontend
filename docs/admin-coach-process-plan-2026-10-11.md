# План админки и кабинета тренера — 11 октября 2026

Статус на 12 октября: основные процессы реализованы. Подробности и границы проверки — [отчёт реализации](admin-coach-implementation-2026-10-12.md). Исходный план ниже сохранён для сопоставления.

Цель: сквозной процесс «заявка → контакт → пробное → рекомендация тренера → решение клиента → группа → договор → оплата → продление», с общей историей и согласованными задачами во всех трёх кабинетах.

## Что уже есть

| Кабинет | Реализовано | Что требует согласования с диспетчером |
|---|---|---|
| Администратор | Выбор филиала, CRM-доска, контакты и следующие действия с версиями, квалификация, запись на пробное, конвертация; ученики, группы, расписание, договоры, оплаты, обзор | Общая очередь задач, сопровождение договоров и обещаний оплаты, единый журнал операций пробного, общие фильтры и периоды, отчёты по новым процессам |
| Тренер | Сегодня, расписание, история, посещаемость постоянных и пробных учеников, рекомендации по пробному, отчёт занятия, профиль | Передача результата администратору с контролем обработки, версии в формах пробного, незавершённые действия, фильтры и пагинация истории, единое рабочее время |

Подтверждённые ограничения: история тренера загружает только первые 20 записей за фиксированные последние два месяца; страницы тренера формируют даты через UTC, API передаёт часовой пояс устройства. Формы пробного администратора и тренера не передают ожидаемую версию записи. Их изменения идут через существующий TrialBookingService, тогда как новые операции диспетчера используют TrialWorkflowService с журналом и явным контролем версии.

## Этап 1. Общие правила и данные — P0

1. Согласовать команды пробного для всех ролей в модуле trial: разрешённые переходы, запрет ранней отметки, проверка доступности рекомендованной группы, версия записи, единый журнал с автором и ролью. Существующий `@Version` сохранить; добавить ожидаемую версию в DTO/команды и понятный ответ 409. При конфликте формы сохраняют ввод.
2. Админские API сопровождения договоров и очереди задач подключить через общие порты владельцев CRM/client/trial/payments. Ограничить их выбранным доступным филиалом. Не обращаться из admin напрямую к dispatcher-контроллерам или его репозиториям.
3. Определить правила появления и закрытия задач: контакт с лидом, итог пробного, следующий контакт, долг, обещание оплаты, продление. Повторное событие не создаёт дубль; состоявшаяся оплата пересчитывает долг и актуальность задачи, а не удаляет историю контактов.
4. Везде применять бизнес-время Asia/Almaty, общий выбор периода и серверную сортировку до пагинации. «За всё время» поддерживать отсутствием границ в API, а не искусственной начальной датой.
5. Разделить полномочия: тренер отмечает посещение и педагогическую рекомендацию; администратор фиксирует коммерческий результат, договор и оплату; диспетчер контролирует и перераспределяет работу. История одна, набор доступных действий зависит от роли.

Готовность: изменение пробного любой разрешённой ролью видно двум другим; журнал содержит автора; устаревшая форма получает 409; чужой филиал и чужое занятие недоступны.

## Этап 2. Рабочее место администратора — P1

| Раздел | Доработка | Формат и сводка |
|---|---|---|
| Главная / задачи | Очередь «мои / филиал», сегодня, просрочено, без ответственного; открытие нужной рабочей формы | Таблица; счётчики по категориям и просрочке |
| Лиды | Полученные от диспетчера назначения, причина передачи, общий контакт и следующий шаг; фильтры владельца, срока и периода | Сохранить канбан, добавить табличный режим; сводка требует контакта / без шага |
| Пробные | Посещение, рекомендация тренера, коммерческий результат, следующий контакт, запись повторного пробного и конвертация | Таблица с датой, статусом и ответственным; сводка сегодня / без посещения / без результата |
| Договоры / долги | Общий план сопровождения, обещанная дата оплаты, контакт, продление, ответственный и история | Таблица; долг отдельно по валютам, обещания сегодня, истекающие за 14 дней |
| Группы / расписание | Вместимость и свободные места с учётом дат состава, подбор после пробного, конфликты расписания | Реестр и календарь; сводка полных групп и свободных мест |
| Ученик / клиент | Общая история по точному ID ученика: лид, пробное, рекомендация, договор, оплаты и контакты | Существующие страницы деталей; не смешивать детей одного клиента |

Готовность: администратор видит назначенную диспетчером работу, выполняет её из своего кабинета; результат изменяет ту же очередь и историю у диспетчера.

## Этап 3. Рабочее место тренера — P1

1. «Сегодня»: удобные на телефоне карточки занятий; отдельные показатели неотмеченной посещаемости, незаполненных отчётов и пробных без рекомендации. Не выводить готовность отчёта только из статуса занятия.
2. Занятие: компактный список учеников и пробных, явное различие «не отмечен / присутствовал / отсутствовал», сохранение несохранённого ввода при ошибке и конфликте. Проверить допустимость завершения занятия при незаполненной посещаемости/отчёте и согласовать правило в домене.
3. Пробные: рекомендация, подходящая группа, комментарий; после сохранения появляется работа для администратора. Тренер видит, обработана ли рекомендация и какой итог зафиксирован, в пределах своих учеников и занятий.
4. История: периоды включая «за всё время», группа, статус занятия, готовность отчёта, сортировка и настоящая пагинация. На компьютере таблица, на телефоне краткие строки/карточки.
5. Расписание: согласованное время, фильтр группы, понятные отмены и изменения. Использовать существующую инфраструктуру уведомлений после проверки её доставки, без отдельной параллельной системы.

Готовность: тренер завершает посещаемость и рекомендацию с телефона; администратор сразу получает следующий шаг; история показывает больше 20 записей и корректный день около полуночи Алматы.

## Этап 4. Единый дизайн и аналитика — P2

- Общие заголовки, панели фильтров, кнопки, статусы, таблицы, пустые состояния и сводки по образцу сотрудников диспетчера. Карточки — для показателей, подробностей и мобильных занятий; реестры — таблицы.
- Вынести общие компоненты периода, фильтров и графиков из dispatcher в shared, сохранив разграничение доменных API.
- Администратор: MUI X Charts для конверсии заявок/пробных, поступлений по валютам, задолженности и посещаемости своего филиала. Чётко подписать период и базу расчёта; не складывать разные валюты.
- Тренер: посещаемость и загрузка собственных групп, выполненные занятия и отчёты. Финансовые данные не включать в кабинет тренера.
- Параметры фильтров сохранять в URL; сводки считать по всему выбранному набору, а не по текущей странице.

## Сквозные приёмочные сценарии

1. Диспетчер назначает лид → администратор фиксирует контакт → записывает на пробное → тренер отмечает посещение и рекомендацию → администратор фиксирует решение, конвертирует, оформляет группу/договор/оплату → диспетчер видит актуальные очередь, отчёт и загрузку.
2. Неявка → контакт с клиентом → новое пробное, без ложной успешной конверсии и без потери истории первого занятия.
3. Обещание оплаты → частичная оплата → пересчёт остатка → полная оплата; актуальность задач меняется, история остаётся.
4. Два кабинета редактируют одну запись: вторая запись получает 409, введённые значения не пропадают.
5. Другой филиал, чужое занятие, отключённый сотрудник: отказ доступа и отсутствие чужих данных в сводках.
6. Два ребёнка одного клиента: рекомендации и история пробных привязаны к нужному ребёнку.
7. Период без границ, границы месяца и полуночь Алматы; сортировка до пагинации, мобильная ширина, клавиатура и доступность графиков.

Рекомендуемый порядок реализации: общие правила → задачи и пробные администратора → пробные и посещаемость тренера → сопровождение договоров → дизайн, фильтры и аналитика → сквозная проверка всех ролей на отдельной QA-базе.
