# Лиды: обновление интерфейса и проверка процессов

Проверка: 11–12 сентября 2026. Локальный стенд, реальный backend и PostgreSQL; тестовая учётная запись администратора. Изменения не опубликованы.

## Что изменилось

- Карточка лида: участники, пробные, пожелания и последние события в основной колонке; контактное лицо и сведения об обращении — справа. Отдельный раздел полной истории, видимое следующее действие и закреплённые кнопки этапа.
- Шесть окон лида приведены к общей боковой панели: создание, уточнение, план/контакт, пробное, оформление участника, отказ. Одинаковые заголовки, фиксированные кнопки, прокрутка формы, закрытие Escape и управление фокусом.
- Создание сокращено с четырёх шагов до трёх: контакт → участники → проверка. Добавлен выбор пола и подготовки, несколько участников в одной заявке. Даты рождения проверяются, ошибки доступны после попытки продолжить.
- Список/воронка, поиск по участнику и контактам, фильтры, сохранение выбранного представления, предпросмотр без потери очереди. На телефоне сводка свёрнута, чтобы записи были видны раньше.
- План работы: приоритет, следующее действие, срок, запись результата контакта и завершение задачи. Отсутствие ответа не переводит новый лид в работу; успешный контакт переводит. Конфликт устаревшей версии задачи возвращает 409.

Дизайн использует общие компоненты shadcn проекта, без параллельной UI-библиотеки. Ориентиры: [карточки записей Attio](https://attio.com/help/reference/managing-your-data/records/create-and-view-records), [иерархия интерфейса Linear](https://linear.app/now/behind-the-latest-design-refresh), [воронка Pipedrive](https://www.pipedrive.com/en/features/pipeline-management). Применены организация информации и акцент на следующем действии, а не копирование брендинга.

## Найдено и исправлено

| Дефект | Исправление / проверка |
| --- | --- |
| Разные размеры и поведение окон лида | Общий LeadModalShell; desktop/mobile, Escape и фокус |
| У взрослого участника всегда задавался мужской пол | Явный выбор пола в форме |
| Будущая / некорректная дата рождения проходила клиентскую проверку | Общая валидация и ограничения календаря; unit и браузерный негативный сценарий |
| Кнопки блокировали отправку без объяснения отсутствующих данных | Проверка при попытке продолжить, подсказки у полей |
| Ошибка оформления клиента была скрыта за модалкой | Ошибка показывается внутри формы |
| После успешного сохранения и сбоя обновления можно было повторить создание | Отдельное состояние «сохранено» и повтор только обновления |
| Кнопка раскрытия списка не имела доступного имени | Исправлен общий combobox |
| Подписи DatePicker терялись внутри FormControl | Передаются id и ARIA-связи на input |
| Бледные подписи / заголовки таблиц | Повышен контраст в проверенных компонентах |
| Меню «Действия» оставалось поверх открываемого окна | Закрытие меню и корректная передача фокуса; проверены перенос и отмена пробного |
| Поиск занятий за 60 дней нарушал лимит API в 31 день | Два непрерывных диапазона по 30 дней |
| Перенос пробного зависел от часового пояса устройства | Проверка времени занятий и календарной даты по Алматы |
| URL мог открыть недоступное действие отменённого пробного | Проверка capabilities при рендеринге формы; backend остаётся источником прав |
| Рекомендованную группу требовалось вводить UUID | Выбор активной группы по названию |
| Следующий контакт после пробного можно было назначить в прошлое | Валидация будущего времени; семь unit-сценариев |
| Выбранный клиент договора мог отсутствовать среди первых 100 записей | При переходе из лида клиент загружается непосредственно по ID |
| Повтор активации после ошибки мог создать второй договор | Сохранение ID созданного черновика и повтор только активации; проверено имитацией 503 |
| Аватары ломались через dev proxy | Сохранён путь /api/media для media-контроллера |
| Избыточные preload и пустые vendor-файлы | Пересобрано разбиение зависимостей; проверка production-сборки |

## Проверенные сценарии

1. Вход, выбор рабочего филиала, список, поиск без результатов, фильтры, сброс, список/воронка, сворачивание колонок, предпросмотр, полная карточка и возврат.
2. Создание ребёнка через UI, будущая дата рождения, добавление/удаление второго участника без сохранения; реальное сохранение одной QA-заявки.
3. План без срока → ошибка; сохранение срока и приоритета → проверка после перезагрузки; устаревшая версия → 409; чужой филиал → 403.
4. Контакт «нет ответа» сохраняет NEW; «связались» переводит в IN_PROGRESS. Уточнение дней и времени, сохранение заметки, завершение задачи и история.
5. Отказ: обязательность причины и комментария для «Другое», отмена окна. Оформление: проверка выбора существующего клиента; затем реальное создание QA-клиента и ученика.
6. Назначение на реальное будущее занятие, переход в карточку пробного, перенос на другое занятие и отмена с причиной. Тестовые пробные отменяются, записи истории не удаляются.
7. Лид → клиент/ученик → форма договора с предзаполнением. Сбой активации договора проверен **через перехват запросов в Playwright**, без создания настоящего договора: два вызова активации и один вызов создания.
8. Десять разделов на desktop/mobile: главная, пробные, клиенты, ученики, группы, расписание, тренеры, договоры, платежи, профиль — загрузка, отсутствие pageerror, неожиданных API 4xx/5xx и горизонтального переполнения страницы.

## Результаты

- Backend: 229 тестов, 0 ошибок / падений / пропусков.
- Frontend: 47 тестов, все проходят; TypeScript, ESLint, сборка и git diff --check проходят.
- Production E2E: 5 тестов проходят, 1 намеренно пропущен — повтор бизнес-записей на мобильном. Мобильный UI проверяется отдельными сценариями, это Chromium с размером iPhone 13, не настоящий Safari.
- Axe WCAG 2 A/AA и 2.1 AA: 0 найденных нарушений в проверенных состояниях списка, карточки и форм. Это не сертификат полной доступности сайта.
- npm audit и npm audit --omit=dev: 0 известных уязвимостей на момент проверки.

### Загрузка

До изменения разбиения: 155 JS-файлов всей сборки, 63 preload-ссылки в HTML, HTML 6699 байт. После: 122 JS-файла, 1 preload, HTML 576 байт. Это структура сборки, **не число всех запросов страницы**: зависимости маршрутов продолжают загружаться динамически.

Последний локальный замер production-сборки при переходе на список после авторизации, без замедления сети/CPU: desktop TTFB 4 мс, DOMContentLoaded 23 мс, FCP 144 мс; mobile-эмуляция 4 / 15 / 72 мс. Общие зависимости уже могли быть в кэше. Эти числа нельзя переносить на интернет, реальные телефоны или считать замером production Core Web Vitals. Lighthouse, полевой INP/LCP и нагрузка больших филиалов в этом прогоне не измерены.

## Границы и следующий этап

- Логика лидов остаётся в CRM, пробные — в trial; интеграция backend проходит через application services и ports согласно архитектуре проекта. Новая миграция добавляет рабочие поля лида; существующие миграции не переписывались.
- Не проведён полный финансовый цикл реального договора: активация, частичная оплата, переплата, возврат, расторжение. Следующий самостоятельный блок — именно договоры и платежи на отдельной тестовой базе.
- Не проверены все роли, гонки между разными бизнес-процессами и все комбинации нескольких участников. Проверка версии задачи не означает общую защиту всех изменений лида от гонок.
- В workspace весь набор лидов филиала пока загружается целиком; порционная отрисовка не заменяет серверную пагинацию.
- Старые несогласованные записи lead/trial не исправлялись массово. Нужна отдельная сверка данных перед миграцией рабочего окружения.
- Нет полной проверки реальным скринридером, Safari/Firefox, клавиатуры телефона и всех модалок остальных разделов.
- В локальной БД остались явно названные QA Workspace-заявки и связанные QA-клиенты/ученики. Тестовые пробные отменены. Настоящие договоры и платежи этим прогоном не создавались.
- Shiplight, Stark, Testifly и внешние платные сервисы не подключались; использованы локальные Playwright и axe. Ссылки WhatsApp/email/телефона только открывают приложение, сообщения автоматически не отправляются.
